Abstract & Executive Summary

Turnaround time is the predominant metric used to measure code review velocity. However, flat arithmetic metrics like "time-to-merge" fail because they do not control for pull request complexity or reviewer workload. This creates perverse incentives that encourage superficial "LGTM" approvals on trivial PRs while penalizing thorough reviews on large changes. RevAudit introduces size-controlled median baselines using live data from GitHub's REST API v3. By segmenting PRs into complexity cohorts, computing non-parametric medians with 90% confidence intervals, and flagging PRs exceeding 1.5× group medians, RevAudit delivers statistically rigorous code review audits without relying on external databases.

1. Problem Formulation: Invisible Variation

In modern collaborative software development, naive service-level metrics (e.g., "PRs must merge within 24 hours") create critical dysfunctions:

  • Uncontrolled Confounders: A 10-line bug fix taking 48 hours indicates severe queue stagnation; a 2,000-line database refactoring taking 48 hours represents rapid turnaround. Flat metrics equate these cases.
  • Perverse Review Incentives: Engineers are incentivized to approve trivial PRs quickly to optimize metrics, while delaying complex, high-risk PRs.
  • Right-Skewed Distributions: Turnaround times follow heavy-tailed distributions (log-normal or Pareto). Arithmetic means are heavily skewed by extreme outliers, necessitating median-based non-parametric baselines.

2. Mathematical & Statistical Engine

RevAudit executes a 5-stage statistical pipeline on live repository pull requests:

2.1 Survival Bias Cleaning (Missing Data Imputation)

PRs closed without merging (abandoned branches or rejected PRs) distort review effort. They are automatically discarded: df[df['merged_at'].notna()].

2.2 Review Effort Latency

Review Time (hours) = (Timestamp(merged_at) - Timestamp(created_at)) / 3600

2.3 Complexity Cohort Stratification

PRs are stratified by description character length (L) as a complexity proxy:

  • Small Cohort: L < 250 characters (minor fixes, typo corrections)
  • Medium Cohort: 250 ≤ L < 1000 characters (standard features)
  • Large Cohort: L ≥ 1000 characters (major architectural refactorings)

2.4 Non-Parametric Median & 90% Confidence Interval

For each cohort, the median review duration (˜x) is calculated along with a 90% confidence interval:

CI_90 = [ max(0, ˜x - 1.645 × (s / √n)), ˜x + 1.645 × (s / √n) ]

2.5 Anomaly Flagging Heuristic (1.5× Rule)

IsAnomaly = True  if  ReviewTime > 1.5 × (Cohort Median)
Variance Ratio = ReviewTime / (Cohort Median)

6. Conclusion

RevAudit proves that software engineering metrics cannot rely on crude averages. By segmenting PRs into size-controlled cohorts and evaluating review duration against non-parametric medians with confidence intervals, the system reveals true review bottlenecks while filtering out superficial noise.
