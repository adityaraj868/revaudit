1. Abstract

Pull request (PR) review is a queueing process, but most engineering dashboards measure only time-to-merge or average review duration. Those metrics conflate code complexity, reviewer workload, abandoned work, and open PRs that have never been reviewed. They also create perverse incentives: trivial changes are approved quickly while large, high-risk changes are delayed.

RevAudit is a full-stack analytical system that measures time to first human review rather than time-to-merge. It samples GitHub pull requests, enriches them with timeline and review events, treats unreviewed and open PRs as right-censored observations, and estimates cohort baselines with Kaplan–Meier medians and bootstrap 95% confidence intervals. It classifies PRs by changed lines and files, fits a Huber robust regression on log-transformed first-review latency, and reports process triage signals alongside a workload-adjusted threshold:

Dynamic_Threshold = 1.5 + (0.15 × active_prs_in_queue)

The implementation consists of a FastAPI backend with GitHub OAuth, Supabase/Postgres persistence, signed webhook ingestion, and PDF export; and a React single-page application with protected reviewer, contributor, and manager dashboards, a smart triage queue, a complexity coach, and a print-ready manager report. The system is deployed with the frontend on GitHub Pages, the API on Render, authentication and PostgreSQL on Supabase, and GitHub webhooks for closed-PR ingestion.

Verification includes 22 backend tests, browser-level end-to-end checks of routing, role gates, queue ordering, complexity warnings, and print behaviour, plus live audits against public repositories and persistence/history checks against PostgreSQL. The report also documents the statistical assumptions, deployment configuration, ethical boundaries, and remaining gaps, including the distinction between route-based role views and true role-based access control.

Keywords: code review, review latency, survival analysis, Kaplan–Meier, right-censoring, robust regression, reviewer workload, GitHub API, FastAPI, React, Supabase, deployment.

2. Introduction

2.1 Problem Statement

Software teams routinely track “time-to-merge” as a proxy for review health. The metric is easy to compute from GitHub and easy to display, but it is not a review metric. It measures the entire lifecycle: implementation, CI, author revisions, review waits, approval delays, and merge policy. A ten-line bug fix that waits two days and a two-thousand-line refactor that merges in two days receive the same score, even though the first indicates queue stagnation and the second may indicate excellent review throughput.

Three confounders dominate:

  1. PR size. Larger changes require more reading, more context, and more iterations. Comparing raw review times across sizes is misleading.
  2. Reviewer workload. A reviewer carrying several active PRs cannot provide the same latency as an idle reviewer. Queue pressure is not a property of the PR.
  3. Survivorship and censoring. Open or closed-without-review PRs are often dropped from “completed review” averages. Dropping them systematically underestimates queue latency because the slowest cases disappear.

The result is a metric that rewards superficial approvals on trivial PRs and penalizes thorough review of complex work.

2.2 Project Objectives

RevAudit was built with the following objectives:

  1. Define and compute a defensible primary outcome: time from review eligibility to the first human review.
  2. Preserve open and unreviewed PRs as right-censored observations instead of discarding them.
  3. Control for PR scope using changed lines and changed files, with explicit Unknown cohorts when metadata is missing.
  4. Estimate cohort baselines non-parametrically and report uncertainty only when the sample supports it.
  5. Model latency conditionally on scope, contributor experience, and recent reviewer activity using a robust regression.
  6. Add a transparent workload-adjusted threshold derived from observable review request evidence.
  7. Persist audits and webhook deliveries in a relational database for historical queries.
  8. Provide separate contributor, reviewer, and manager experiences without turning the dashboard into an individual performance scorecard.
  9. Be deployable with managed services: GitHub Pages, Render, Supabase, and GitHub webhooks.

2.3 Scope

The system analyzes public repositories through unauthenticated GitHub API access and private or higher-rate repositories through a user token or OAuth session. The unit of analysis is a pull request. The primary statistical output is a set of cohort baselines, adjusted triage signals, and workload metrics. The system does not attempt to measure code quality, reviewer competence, or individual productivity.

2.4 Contributions

  • A censoring-aware review-latency pipeline built on GitHub's public REST API.
  • A hybrid statistical engine combining Kaplan–Meier estimation, bootstrap intervals, Huber robust regression, and a workload-adjusted ratio rule.
  • A persistence and webhook layer that converts a stateless analysis endpoint into a historical audit system.
  • A role-oriented frontend with distinct workflows for contributors, reviewers, and managers.
  • A deployment blueprint spanning Supabase Auth/PostgreSQL, Render, and GitHub Pages.
  • A reproducible verification suite covering statistics, persistence, webhook signatures, PDF generation, and browser-level UI behaviour.

3. Background and Related Concepts

3.1 Review Latency

Review latency is a queueing metric. In a single-reviewer queue, the waiting time depends on arrival rate, service time, and the reviewer's current backlog. In a multi-reviewer repository, assignment policy and reviewer availability dominate. Time-to-merge includes several stages after the first review, so it is not a clean measure of queue delay.

RevAudit therefore defines the primary outcome from the moment a PR becomes eligible for review to the moment a non-bot human submits the first review. For draft PRs, eligibility begins at the first ready_for_review event.

3.2 Right-Censoring and Survival Analysis

If a PR has not received a first review by the audit timestamp, its true latency is unknown but at least the observed age. Discarding it biases the sample toward fast reviews. Right-censoring retains that lower bound.

The Kaplan–Meier estimator handles censored observations by updating survival at each event time using the number still at risk. The median is the first time the estimated survival drops to or below 0.5.

3.3 Robust Regression

Review latency is heavy-tailed. Ordinary least squares is sensitive to extreme outliers and to leverage points. RevAudit models log(1 + hours) with a Huber M-estimator using iteratively reweighted least squares. Residuals are standardized with the median absolute deviation, and large absolute residuals are reported as triage signals rather than causal findings.

3.4 Reviewer Workload

GitHub exposes review requests and review events, but not a complete historical view of every reviewer's assignment queue. RevAudit uses two observable proxies:

  • Recent activity: the number of human reviews submitted by the eventual first reviewer in the seven days before the first review.
  • Active queue at creation: other sampled PRs that were still open at this PR's ready-for-review time and already had an explicit review request for the eventual first reviewer.

Both are transparent and bounded by the sampled window. Neither claims to be a complete assignment history.

3.5 Role-Based Analytics

Different stakeholders ask different questions:

  • Contributors want to know whether their PRs are waiting, which are active, and how to prepare a reviewable change.
  • Reviewers want an actionable queue ordered by review cost and age.
  • Managers want cohort baselines, adjusted signals, and a printable summary.

A single dashboard forces all three into one view. RevAudit separates the workflows by route while keeping a shared data payload.

5.2 Request Flows

Audit flow

  1. The SPA requests /api/audit?owner=<owner>&repo=<repo> with optional bearer token.
  2. FastAPI selects the token: bearer header, server-side OAuth session, or GITHUB_TOKEN.
  3. The GitHub client paginates /repos/{owner}/{repo}/pulls (100/page) up to the requested sample limit.
  4. Each PR is enriched with /pulls/{number} (change size) and /issues/{number}/timeline (review events, review requests, ready-for-review).
  5. Records are normalized, censored, and passed to the statistical engine.
  6. Baselines, robust model, workload thresholds, stage metrics, and anomalies are computed.
  7. The response is cached for five minutes when unauthenticated.
  8. A background task mirrors the payload into PostgreSQL.

Webhook flow

  1. GitHub sends pull_request.closed with X-Hub-Signature-256.
  2. FastAPI verifies the HMAC in constant time.
  3. The endpoint returns 200 immediately.
  4. A background task fetches the PR detail, timeline, and reviews with GITHUB_TOKEN, builds a record, and upserts it.

Auth flow

  1. The frontend starts Supabase GitHub OAuth with repo read:user scopes.
  2. Supabase redirects back to the Pages URL with a session.
  3. The SPA stores the GitHub provider_token and attaches it as a bearer token.
  4. The backend validates it against GitHub and uses it for audits.

6. Data Ingestion and Persistence

6.1 GitHub REST Integration

The audit endpoint requests recent PRs with:

GET /repos/{owner}/{repo}/pulls
    ?state=all
    &sort=created
    &direction=desc
    &per_page=100

Pagination follows the Link: rel="next" header. The sample limit is user configurable up to 200, but unauthenticated requests are capped at 25 PRs to avoid exhausting GitHub's 60 requests/hour IP limit. Authenticated requests use the 5,000 requests/hour budget.

6.2 Per-PR Enrichment

For each PR, the backend requests:

  • GET /repos/{owner}/{repo}/pulls/{number} — additions, deletions, changed files.
  • GET /repos/{owner}/{repo}/issues/{number}/timeline — reviews, author comments, review requests, ready-for-review events.

Enrichment runs in batches of six PRs with three worker threads. A rate-limit response stops further enrichment and marks the audit partial; the partial sample is still returned with explicit warnings.

6.3 Normalization

Each record stores:

  • identity: PR number, title, author, association, URL, state;
  • timing: created, ready-for-review, merged, closed, first review;
  • scope: additions, deletions, changed lines, files, cohort;
  • review history: human reviews, review requests, rounds;
  • censoring: whether a first review was observed and why not;
  • derived: latency, workload proxy, thresholds, model prediction.

Bot authors ([bot], Dependabot, Renovate, GitHub Actions, Codecov, etc.) are excluded from cohort and model estimates. Bot reviewers are ignored. The PR remains in the sample totals but does not influence baselines.

6.4 Censoring Rules

  • If a first human review exists: event observed, latency computed.
  • If no review and the PR is open: right-censored at audit time.
  • If no review and the PR is closed unmerged: censored at closure.
  • If the timeline could not be fetched: the PR is excluded from survival estimates and a warning is emitted.

6.5 Relational Schema

Five tables are used:

Table Purpose
repositories Owner/name, default branch, last sync
users GitHub identity, avatar, login
pull_requests One row per PR with scope, timing, review, and workload fields
review_events Human review events with state and timestamp
auth_sessions Hashed session ID and encrypted OAuth token

The pull_requests table includes Phase 3 fields: reviewer_queue_at_creation, dynamic_threshold_ratio, dynamic_threshold_hours, workload_ratio_to_median, and is_workload_anomaly.

6.6 Idempotency and Concurrency

Audit persistence and webhook ingestion may overlap. The persistence module:

  • serialises writes with a process-wide lock;
  • uses savepoints and retries when a unique constraint is violated;
  • upserts users, repositories, PRs, and reviews;
  • deduplicates reviews by GitHub review ID when available, otherwise by reviewer, state, and timestamp.

This prevents duplicate users or PRs when a background audit and a webhook arrive together.

6.7 Caching

Unauthenticated, non-refreshed audits are cached in memory for five minutes, with a maximum of 64 entries. Authenticated requests are not cached because the result depends on the user's token and permissions.

7. Statistical Methodology

7.1 Primary Outcome

For PR i in cohort C:

eligible_at_i = first ready_for_review event, or created_at
first_review_at_i = earliest non-bot human review
Δt_i = (first_review_at_i − eligible_at_i) / 3600 hours

If no human review exists, Δt is the observed age at closure or audit time and the observation is right-censored.

7.2 Scope Cohorts

churn = additions + deletions
Small   : churn ≤ 100    and files ≤ 5
Medium  : churn ≤ 1000   and files ≤ 20
Large   : above either medium threshold
Unknown : diff metadata unavailable

The description-length thresholds (250 / 1,000 characters) are used only by the contributor Complexity Coach as drafting guidance, not by the statistical engine.

7.3 Kaplan–Meier Median

Records are sorted by time. At each event time:

S(t) = S(t_prev) × (1 − events_at_t / at_risk_at_t)

The median is the first event time where S(t) ≤ 0.5; otherwise the median is reported as median_not_reached.

7.4 Bootstrap Confidence Interval

When a cohort has at least 10 records and at least 5 events, the engine draws 500 bootstrap resamples of the Kaplan–Meier median and reports the 2.5th and 97.5th percentiles as a 95% interval. If too few resamples produce a median, the interval is reported unavailable. This is a non-parametric interval, not a fabricated standard-error approximation.

7.5 Huber Robust Regression

The model uses observed first reviews with complete scope and activity data:

y_i = log(1 + Δt_i)
x_i = [1, log1p(churn), log1p(files),
       first_time_contributor, log1p(reviewer_activity_7d)]

A Huber M-estimator is fitted with iteratively reweighted least squares. Residuals are centered on the median and scaled by 1.4826 × MAD. A PR is a triage signal when |z| ≥ 2.5, in either direction. The model requires at least 25 observations with variation; otherwise it reports insufficient_data or insufficient_variation instead of failing silently.

7.6 Workload-Adjusted Threshold

For each PR with a first reviewer and a ready time:

  1. Gather explicit review_requested events for that reviewer across sampled PRs.
  2. Count other sampled PRs that were open at this PR's ready time and had already requested that reviewer.
  3. Let that count be Q. Apply:
Dynamic_Threshold = 1.5 + (0.15 × Q)
threshold_hours = Dynamic_Threshold × cohort_median

A PR is workload-flagged when its first-review latency exceeds threshold_hours. The engine reports request_coverage_pct; if explicit review-request evidence is missing, the queue is not asserted and coverage is shown as low.

7.7 Stage Metrics

  • Request → first review: from the latest review request before the first review.
  • Author response after review: first author issue comment after the first review (a comment proxy, not a code-change measure).
  • Approval → merge: from the latest approval to merge.

7.8 Workload Summary

For PRs with a first review, the engine reports:

  • average and maximum recent reviewer activity;
  • Pearson correlation between activity and first-review latency;
  • OLS slope in hours per additional recent review;
  • sample size and review-event count;
  • an explicit definition of the proxy.

7.9 Interpretation

The system reports process signals, not quality scores. A long latency may reflect queue pressure, unclear requirements, CI failures, time zones, or reviewer availability. A short latency does not prove a thorough review. This framing is implemented in the UI copy, the manager report, and the ethical safeguards view.

8.3 Authentication and Rate Limits

Two authentication paths coexist:

  1. Supabase OAuth (primary for deployment): the SPA obtains a GitHub provider_token, stores it, and sends it as Authorization: Bearer.
  2. Backend OAuth fallback: /auth/github/login and callback create an encrypted AuthSession; the browser receives an HttpOnly session cookie.

The audit endpoint uses the first available token: bearer header, session token, or GITHUB_TOKEN. Without a token, samples are capped at 25 PRs. OAuth sessions last 30 days; tokens are encrypted with Fernet using a key derived from SESSION_SECRET. Session cookies use SameSite=None when COOKIE_SECURE=true so the Pages frontend can talk to Render cross-site.

8.4 Parallel Enrichment and Error Handling

GitHub requests time out after 20 seconds. Enrichment uses a thread pool to reduce wall-clock time. A 404 produces an actionable message; 403/429 responses expose rate limit reset information; network errors become 502 responses. A rate limit during enrichment marks the result partial rather than discarding the whole audit.

8.5 PDF Reporting

POST /api/reports/pdf accepts the audit JSON and renders:

  • repository and audit metadata;
  • PR/merged/first-review/censoring counts;
  • cohort baseline matrix with 95% intervals;
  • robust triage signals;
  • workload-adjusted threshold matrix;
  • workload snapshot and interpretation notes.

The exporter handles missing medians, missing intervals, and legacy payloads. The manager dashboard additionally supports native browser printing with a dedicated @media print stylesheet.

8.6 Configuration

Environment variables are documented in Appendix C. Production requires DATABASE_URL, GITHUB_TOKEN, FRONTEND_URL, SESSION_SECRET, COOKIE_SECURE=true, GITHUB_WEBHOOK_SECRET, and PERSIST_AUDITS=true. OAuth fallback credentials are optional when Supabase Auth is used.

9.4 Reviewer Dashboard

The Smart Triage Queue orders PRs by cohort (Small → Medium → Large → Unknown), then by open status and age. Small PRs are pinned to encourage rapid unblocking. Modes:

  • Actionable queue — open PRs without a first review;
  • All awaiting — all sampled PRs without a first review;
  • All sampled — every PR in the payload.

Each row shows the author, cohort, age, first-review state, expected latency, queue at creation, workload multiplier, and a workload-adjusted signal badge.

9.5 Contributor Dashboard

The contributor view accepts an exact GitHub username and also pre-fills the signed-in user. It displays:

  • currently active PRs;
  • median first-review latency;
  • adjusted triage signals;
  • a table of the contributor's sampled PRs with observed, expected, and censored states.

The Complexity Coach provides live feedback on a draft description:

  • under 250 characters → Small drafting range;
  • 250–1,000 → Medium;
  • over 1,000 → Large warning with advice to split the change.

The coach states explicitly that body length is a drafting heuristic; the engine's cohorts use changed lines and files.

The manager report retains the size-stratified anomaly matrix and adds:

Print / Save as PDF invokes the browser print dialog. The print stylesheet hides navigation, header, footer, and action buttons, converts backgrounds to white, and avoids page breaks inside tables and sections.

12. Results and Discussion

12.1 What the System Demonstrates

The implementation demonstrates four shifts from a naive review dashboard:

  1. From merge time to first-review latency. The primary outcome isolates the review queue from implementation and merge policy.
  2. From complete-case averages to censoring-aware estimation. Open and unreviewed PRs remain in the estimate instead of vanishing.
  3. From raw size buckets to adjusted signals. Scope, experience, and recent reviewer activity are modeled explicitly.
  4. From a single dashboard to role workflows. Contributors, reviewers, and managers see different tasks over the same data.

12.2 Case Study: fastapi/fastapi

A 10-PR sample produced seven merged PRs, two closed unmerged, and one open PR. No first human review appeared in the sample, so all ten observations were censored. Cohorts were populated (Small 1, Medium 5, Large 1), but the robust model correctly reported insufficient data. A later 25-PR audit was persisted and served from /api/history.

This case illustrates a strength of the design: the system does not invent a median when no events are observed. It reports censoring, coverage, and warnings instead of a false precision.

12.3 Case Study: django/django

An 8-PR sample contained three observed first reviews (1.39 h, 0.77 h, 18.23 h) and five censored PRs. The observed median was 1.39 h. Workload coverage was 0% because no explicit review_requested events for the eventual first reviewer appeared in the sampled timeline, so the engine reported a low-coverage warning and did not assert a queue.

This case shows the value and the limits of the workload proxy: absence of evidence is surfaced rather than treated as an empty queue.

12.4 Case Study: pallets/flask and kubernetes/kubernetes

Recent samples contained no first reviews, leaving all PRs censored. Cohort counts and warnings were still produced. The UI remains useful as a queue view, but no latency baseline is claimed. This is the correct statistical behaviour.

12.5 Performance

  • Enrichment is parallelized in small batches to reduce wall-clock time.
  • The five-minute cache avoids repeated identical audits.
  • Postgres persistence runs after the response, so the dashboard is not blocked by database writes.
  • The free Render tier introduces cold-start latency; skeletons and the toast make this visible rather than opaque.
  • Schema creation against the pooled Postgres connection took several seconds on first startup, then reused the schema.

12.6 Threats to Validity

  • Sampling bias. Recent PRs are not a random sample of repository history.
  • Incomplete review-request history. The queue proxy is bounded by the sampled window and explicit timeline events.
  • Team reviews. GitHub team review requests are not resolved to individuals.
  • Missing timelines. Rate limits or permissions can remove PRs from survival estimates.
  • Model assumptions. Huber regression describes association, not causation.
  • Small samples. Live validation samples were small; they demonstrate behaviour, not repository-level conclusions.
  • Role authorization. The role routes are not enforced by identity or backend permissions.

13. Ethics, Privacy, and Governance

13.1 Blame-Free Framing

The UI and report repeatedly state that signals describe process patterns, not individual performance. Shorter review time is not equated with better review, and longer review time is not attributed to a person's competence. The ethical safeguards view documents this boundary.

13.2 Data Minimization

The system stores public GitHub metadata, review events, and PR scope. It does not store code diffs or review comment bodies except when a webhook payload provides them. It does not post, approve, merge, or modify repositories.

13.3 Token Security

  • Backend OAuth tokens are encrypted with Fernet before storage.
  • Session IDs are hashed before storage.
  • Supabase provider tokens are stored in browser local storage for API calls; they are not sent to the backend database.
  • Webhook requests are authenticated with HMAC-SHA256.
  • Secrets are supplied through environment variables and excluded from version control.

13.4 Access Control Gap

The current role system separates views by route and requires authentication, but it does not enforce role membership. A signed-in contributor can open the manager route. True RBAC would require a role source, per-route checks, and backend authorization. This is documented as a limitation rather than hidden.

13.5 Data Retention

The database retains PR metadata and review events indefinitely unless an operator deletes them. A production deployment should define retention, deletion, and export policies, especially for private repositories.

14. Limitations and Future Work

14.1 Known Limitations

  1. No true role-based access control. Routes are auth-gated but not role-gated.
  2. Sampled queue proxy. Reviewer workload is reconstructed only from sampled PRs and explicit review requests.
  3. Single-repository audit. Cross-repository and organization-level views are not implemented.
  4. No GitHub App installation tokens. Webhooks use a personal token; private organization installations are not modeled.
  5. No webhook retry queue. Failed background ingestions are not retried automatically.
  6. No database migration framework. Schema evolution uses additive ensure_schema logic rather than Alembic migrations.
  7. Legacy modules remain. analytics.py and parts of github_client.py are retained from earlier phases and are not on the live audit path.
  8. Small live samples. Validation did not run a large statistical study.

14.2 Future Work

  • Implement RBAC with a role column or Supabase app_metadata, backend dependencies, and per-route guards.
  • Add GitHub App installation tokens and webhook delivery verification/retries.
  • Reconstruct a fuller reviewer assignment history from organization data.
  • Add multi-repository and organization dashboards.
  • Calibrate confidence intervals and validate the robust model on larger samples.
  • Add Alembic migrations and a staging database.
  • Add automated browser tests to CI.
  • Add accessibility and internationalization audits.
  • Add retention/deletion controls for private data.

15. Conclusion

RevAudit replaces a flat time-to-merge metric with a censoring-aware measure of review queue latency. It controls for PR scope, models reviewer activity, reports uncertainty only when the data supports it, and separates the workflows of contributors, reviewers, and managers. The system is implemented end to end: GitHub ingestion, statistical analysis, relational persistence, signed webhooks, PDF reporting, managed authentication, and cloud deployment.

The project also demonstrates the importance of honest negative results. When no first reviews are observed, the engine says so. When workload evidence is missing, it reports low coverage. When the robust model lacks support, it refuses to fit. Those choices make the dashboard less decorative and more trustworthy.

The remaining work is clear: true role-based authorization, fuller assignment history, larger validation samples, and production hardening. The current system provides a solid, deployable foundation for those extensions.
